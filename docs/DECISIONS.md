# DietGate — Decision Log

Every ambiguous choice from the spec, resolved with the simplest option that
satisfies the acceptance criteria. Newest entries at the bottom.

| # | Decision | Reason |
|---|----------|--------|
| D1 | Mock-provider RNG is seeded with a stable hash (`blake2b(seed, task_id, model_id)`) instead of Python's built-in `hash()`. | `hash()` on strings is salted per process (`PYTHONHASHSEED`), which would break the spec's "reruns are reproducible" requirement across processes. |
| D2 | Extra modules beyond the spec layout: `core/config.py` (YAML loading), `core/errors.py` (error types), `core/runtime.py` (component wiring), `sim/runner.py` (in-process simulator for dashboard controls). | Spec rule "one responsibility per file" would otherwise push `settings.py` past 300 lines mixing env + YAML concerns, and `main.py` mixing app wiring. |
| D3 | For paths that never reach an upstream (cache hit, shortcut, auth failure), `overhead_ms` is the full time from receive to response built. | There is no upstream wait to exclude, so every millisecond is gateway overhead by definition (spec section 5 formula degenerates gracefully). |
| D4 | For streamed responses, `t_first_chunk_out` is taken after SSE-encoding the first chunk, before handing it to the ASGI server. | We cannot observe the socket write itself inside ASGI; encode time is the part of forwarding delay we control. |
| D5 | Cache lookup and singleflight dedup apply to **non-stream** requests only. | A cached full `ChatResponse` cannot be replayed chunk-by-chunk without buffering; simplest correct option (spec rule 7). Streaming cache can be added later. |
| D6 | Gateway API keys are enforced by default; `config/app.yaml` ships a demo key `dg-demo-key`. | Spec section 5 step 2 says Bearer must match a key in app.yaml. "Zero API keys" refers to *provider* keys; the demo key is documented in README/.env.example. |
| D7 | Cascade verifier compares the answer against `metadata.mock_expected` when present; without ground truth it accepts the first answer. | A real verifier needs a checker or judge which only the caller can provide in production; in the demo the simulator supplies ground truth. Documented limitation. |
| D8 | Mock skill for `task_type=unknown` defaults to 0.9 when the model has no entry for it. | The safe-default `unknown` route only offers mock-large; a constant keeps the mock deterministic. |
| D9 | Shadow judge in mock mode is a deterministic comparison against `metadata.mock_expected` with zero upstream cost. | Spec section 6.5: "In mock mode the judge is a deterministic comparison against ground truth, to keep the demo free." Real judge models are future work. |
| D10 | A task outcome is applied to **every** (task_type, model) arm the task used. | With cascade, each attempt is a real observation for its own arm; with single-model tasks there is exactly one arm. |
| D11 | Duplicate feedback: the `outcomes` row is replaced; arm stats are adjusted by the delta while the task is still in the learner's bounded in-memory map, otherwise the first label stands. | Spec 6.6 requires idempotency; unbounded per-task memory is not acceptable on a long-running process. |
| D12 | Thompson cost prior before any data: `400 in / 300 out tokens` priced at catalog prices. | The policy needs a cost estimate before observations; the constant is documented, not presented as a measurement. |
| D13 | Beta credible intervals use a normal approximation (mean ± 1.96·sd). | Avoids a scipy dependency for one dashboard number. |
| D14 | The overhead benchmark's headline numbers are the **gateway's own per-request `overhead_ms` percentiles** (read back via `/admin/latency` after a warmup phase); the external client-measured gateway-vs-direct difference is kept only as a concurrency-1 cross-check, and there are no concurrency >= 50 rows. | Subtracting quantiles of two separate runs is unreliable: at concurrency >= 50 the two single-process servers saturate at different points and the difference showed negative "overhead" (queueing order, not routing cost). Cold-start first requests (1-19 ms) made warmup mandatory. The gateway's internal measurement is the spec section 5 definition and needs no cross-run subtraction. |
| D15 | Docker demo starts the simulator automatically (`DIETGATE_AUTO_START_SIM=true`) inside the same container. | Spec phase 9 requires "dashboard fills with data in under 2 minutes" from `docker compose up`; a second container adds orchestration without value. |
| D16 | Default gateway port is 8080 instead of the conventional 8000. | The development machine runs another service on 8000; 8080 avoids a guaranteed first-run collision. |
| D17 | The mock provider intentionally uses seeded, non-cryptographic randomness (`random.Random` on a stable hash; `random.uniform` for latency jitter). | Deterministic, reproducible behaviour is the mock's functional requirement (spec section 7). These draws never protect secrets; anything security-relevant (ids, keys) uses `secrets`/`uuid4`. The same applies to the policy's seeded sampling RNG (spec's convergence test requires a seeded RNG). |
| D18 | Thompson policy: the spec pseudocode exploit branch is kept verbatim, plus (a) a bounded exploration boost (+0.20 eps) during a task type's first 300 labeled outcomes, aimed at the least-tried arm, and (b) widened mock skill margins for extract/classify/summarize in `config/models.yaml`. | Simulations across 8 seeds showed the literal spec numbers (skill 0.92-0.93 vs target 0.90) freeze the cheap arm permanently in half the runs: a single unlucky streak makes its Beta posterior un-eligible and no mechanism revisits it. The boost guarantees cheap arms enough data to prove themselves; widened margins (0.96 vs 0.90) make the target statistically separable (~3σ at n≈100). The spec's expected outcome (extract/classify → mock-small, summarize → mock-medium, reason/code → mock-large) is preserved and now converges 8/8 seeds. |
| D19 | `scripts/run_demo.py` is the primary one-command demo (`run_demo.sh` is a thin bash wrapper). | The development machine is Windows; a Python entry point runs everywhere without shell-specific process handling. |
| D20 | Non-stream responses also carry `X-Dg-Baseline-Cost-Usd` (not in the spec's header list). | The simulator and A/B mode need the per-request baseline to compare savings without re-deriving prices client-side; the header is derived data, not a new metric. |
| D21 | Demo rate limits are raised (`requests_per_min: 6000, burst: 300`). | The first full simulator run hit the original 120/min limit with 429s on ~90% of requests; a demo generating 25 tasks/s needs headroom. Production deployments tune these down; the limiter itself is unchanged and tests cover 429 behaviour. |
| D22 | `/admin/*` reads (dashboard) and the mutating controls use **separate keys**: `admin_key`/`DIETGATE_ADMIN_KEY` vs `control_key`/`DIETGATE_CONTROL_KEY`. Controls additionally require `demo_mode` and are **disabled by default** (empty control key). docker-compose requires a strong `DIETGATE_ADMIN_KEY` and does not set a control key. | A public demo must be watchable but not stoppable/resettable by anyone holding the dashboard key. Env-based keys keep secrets out of the repo (none are committed; verified). |
| D23 | `/admin/summary` savings are computed only over `model: "auto"` (routed) rows; pinned-model requests count towards total spend but not towards savings. | A pinned request already fixed the model - DietGate made no routing decision, so attributing savings to it would inflate the headline number. |
| D24 | Startup guard (`validate_public_safety`): with `DIETGATE_PUBLIC=true` or `demo_mode: false` the app refuses to start if the admin key or any API key is the shipped default or shorter than 16 chars, or if no API key is set. Error messages never print key values. Data-plane keys can come from `DIETGATE_API_KEYS` (comma-separated), which replaces the YAML list. | Defaults are fine for a local demo and dangerous on the internet; failing at boot is safer than documentation. Local `make run` / default compose behaviour is unchanged. |
| D25 | `DIETGATE_PUBLIC_DASHBOARD=true` makes the `/admin/*` **reads** keyless (controls still need the control key). It is refused at startup if any real provider is configured or `store_prompts` is on. | A hiring manager should be able to open the dashboard link without a key, but only synthetic mock data may ever be readable that way. |
| D26 | Real-provider models must declare `price_in_per_mtok` and `price_out_per_mtok` explicitly in `models.yaml`. | A forgotten price silently priced requests at $0 and would corrupt every savings number. `0` stays allowed for free/local models. |
| D27 | Adapter fixes found by reading the code and testing with faked upstreams (`tests/test_real_providers.py`): `httpx[http2]` is now a dependency (a real-provider key crashed startup without `h2`); the Anthropic adapter now sends `stream: true`, keeps `message_start` input tokens in streamed usage, forwards a clamped temperature, and raises on stream `error` events; OpenAI-compatible max-tokens parameter name is configurable (`OPENAI_MAX_TOKENS_PARAM`). | These paths had never run against a real upstream. The fixtures pin the wire format and token accounting; a live smoke test with your own key is `scripts/live_smoke.py`. |
| D28 | The auto-started simulator (docker) runs the 2000-task `default` scenario instead of the 300-task `fast` one; override with `DIETGATE_AUTO_SIM_SCENARIO`. | 300 tasks end inside the exploration phase (about 70% savings, unconverged routing matrix), which undersells the demo and does not match the README's numbers. 2000 tasks at 25/s take about 80 s. |
| D29 | The simulator runner waits for `/healthz` (up to 20 s) before sending traffic. | Found in a real `docker compose up` log: the auto-start runs inside app startup, before the port accepts connections, so the first task failed with connection-refused and was counted as a failed task (1999 of 2000 requests reached the gateway). |
| D30 | `openai_compat` models can carry their own `base_url`, `api_key_env`, `upstream_model`, `extra_body`, `stream_include_usage`; the registry builds one provider per (base URL, key variable). Models whose key variable is unset are not routable. | One global `OPENAI_BASE_URL` could not express OpenAI plus Novita plus vLLM side by side, and the gateway-facing model id often differs from the provider's id. `extra_body` can add request fields but never override `model`/`messages`/`stream`. |
| D31 | `live_smoke.py` fails if `X-Dg-Model` is not the requested model, and defaults to `--max-tokens 1024`. | A failed pinned call silently falls back to another candidate (by design); a smoke test must not pass on that. Always-thinking models return an empty answer when max_tokens is small. |
| D32 | Simulator task ids now carry a per-run random tag (`<scenario>-<tag>-00001`). | Found when a Docker re-run on the persistent volume got worse each time. The sim reused the same 2000 ids every run; outcomes are keyed by `task_id` (INSERT OR REPLACE) and joined to requests, so each new run overwrote the old outcomes and attached them to other runs' requests, corrupting the arm statistics rebuilt on restart. Measured on three consecutive runs over one database: before the fix 2000 distinct task ids for 6000 requests and the share of `reason` traffic sent to the weak `mock-medium` grew 39% -> 43% -> 74%; after the fix 6000 distinct ids and the share fell 31% -> 24% -> 12%. Existing volumes created before this fix hold corrupted statistics: reset with `docker compose down -v`. |
| D33 | Thompson forced exploration only targets arms whose upper 95% credible bound is still >= the task type's quality target (`prune_explore`, default on; never empties the pool; arms with little data keep a wide interval and stay explorable). | With 76-127 tasks per run, `reason`/`code` kept spending a fixed share of traffic on the weaker `mock-medium` even after the data ruled it out, which pulled success under the 90% target. Pairing 40 seeds with and without pruning (same simulated traffic): `reason` 89.1% -> 92.6% (runs at or above 90%: 11 -> 33 of 40), `code` 86.9% -> 91.1% (7 -> 27 of 40), overall success 95.3% -> 95.7%, savings 79.8% -> 78.1% in that harness. Quality up, savings down about 2 points: an explicit trade-off, not a free win. |
| D34 | Dashboard fixes found from a real screenshot: charts use `maintainAspectRatio: false` (the learning curve filled only ~40% of its box: a 2:1 ratio inside a 300 px-high container), are created once and updated in place instead of destroyed every 2 s, the explore-share line has a visible right-hand % axis (it was on a hidden 0-1 axis next to a $ axis), dollar values never use exponent notation or locale decimal commas, the learning curve uses 10 s buckets (about 9 points per 2000-task run instead of 3-4), and the latency chart uses a log scale so a ~0.2 ms gateway overhead is visible next to hundreds of ms of mock model latency. | The screenshot is the first thing a reader sees. Verified by running `app.js` in Node against real `/admin/*` responses with stubbed DOM/Chart (axis config, in-place updates, number formats); the pixels themselves still need a look in a browser. |
| D35 | Merge note: the key guard exists once. The `DIETGATE_API_KEYS` override (`apply_api_keys_override`) and `validate_public_safety` from the earlier "Refuse default credentials" commit are the single implementation; the 16-character minimum for admin/API/control keys and the public-dashboard checks (D24, D25) were folded into `validate_public_safety` (new optional `catalog` argument). Tests that used 8-character demo keys in public mode were given realistic 16+ character keys. | Two parallel implementations of the same guard had been written independently; one validator with one set of messages is easier to audit. |
